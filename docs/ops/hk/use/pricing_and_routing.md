# 價格、成本與線路順序

這一頁講 Modeltaps 如何決定用戶付多少錢、一次請求花你多少成本、請求交給哪條線路，並說明每項設定在哪裡配，最後附算例。

## 三個數

| 數 | 是甚麼 | 誰能看到 |
|---|---|---|
| **目錄價** | 模型的官方 API 價，按每百萬 token（或按次、按分鐘）計 | 所有人，在價格頁 |
| **分組倍率** | 每個用戶分組在目錄價上乘的倍數；`default` 組的倍率就是站點的正常售價 | 用戶看到自己所在分組的價格 |
| **渠道成本** | 上游向你收的錢：渠道標價 ×（1 + 渠道費率） | 只有管理員 |

用戶付的永遠是 **目錄價 × 分組倍率**，不隨承接請求的渠道變化。渠道成本不會轉嫁給用戶：它只決定請求交給哪條線路，以及價格閘攔下哪些線路。

一次請求的毛利：

> 目錄價 × 分組倍率 ×（1 − 收款成本率）− 渠道成本

**收款成本率**是你自己收款時付出的比例（信用卡手續費、換匯損耗）。不向任何人收取，只用來算扣掉收款成本後的淨收入，再拿去和渠道成本比。

## 在哪裡配

| 配甚麼 | 控制台位置 | 設定 / 欄位 |
|---|---|---|
| 目錄價 | **模型目錄** → 某個模型 → 價格；或從價格來源同步 | 模型價格 |
| 站點利潤 | **用戶 → 用戶分組** → `default` 組 → 倍率（1.12 = 比官方價高 12%） | `user_groups.ratio` |
| 折扣組 / 加價組 | **用戶 → 用戶分組** → 其他分組 | `user_groups.ratio` |
| 收款成本率 | **平台設定 → 計費 → 定價** → 收款成本率 | `PaymentCostPercent` |
| 試算 | 同一張卡片：輸入一個預設分組倍率試算（不儲存） | — |
| 渠道標價 | **渠道** → 某個渠道 → 價格（從上游同步）；沒有價格表的中轉：進階 → 成本倍率 | `channel_prices`、`cost_ratio` |
| 渠道費率 | **渠道** → 某個渠道 → 進階 → 渠道費率，或充值記錄 | `fee_rate`、`fee_note` |
| 同一檔如何分擔 | **平台設定 → 網關 → 分配 → 分流方式與成本** → 同一檔內；單個模型在它的「線路」頁籤裡改 | `SupplyModeDefault`、模型的分流方式 |
| 成本與優先級 | 同一張卡片 → 成本與優先級 | `SupplyCostOrder` |
| 檔位順序 | **平台設定 → 網關 → 分配** → 分配策略；手動模型在它的「線路」頁籤裡 | 分配策略、線路優先級 |

上面每項設定的類型、範圍和更多示例都在 [設定參考](../settings/index.md) 裡。AI 助手可以透過 [管理 MCP](./admin_mcp.md) 查詢。

## 渠道費率

渠道費率是渠道商在標價之外另收的比例。多數渠道商在你充值時收，所以：

> 渠道費率 = 實付現金 ÷ 到賬額度 − 1

新建渠道先用渠道商公佈的費率；沒公佈的，用結賬頁上看到的費率：

| 渠道商 | 預設 | 出處 |
|---|---|---|
| Requesty | 5% | 計費文件裡的充值服務費 |
| OpenRouter | 5.5% | FAQ 裡的購買額度手續費（最低 $0.80；加密貨幣 5%） |
| Vercel AI Gateway | 3% | Vercel 文件沒寫，只說手續費由買方承擔；2026-11-18 結賬頁顯示 $100 額度收 $3.00 手續費 |
| 官方廠商 API、其他中轉 | 0% | — |

在 **渠道 → 進階 → 充值記錄** 裡錄入真實充值：實付了多少現金（含信用卡和換匯費），到賬多少額度。之後渠道費率按最近 10 筆充值反推，取代預設值。贈送額度不會令費率變成負數。

## 請求交給哪條線路

1. 先按優先級排（來自分配策略，或手動模型自己的數字）。
2. 設成**成本優先**時，再按成本排（見下文）。
3. 在承接請求的線路之間，看分流方式：**負載均衡**按權重分擔，**主備**全部交給權重最高的。

**成本與優先級**（`SupplyCostOrder`）決定成本參不參與：

- **優先級優先**（預設）：成本不參與排序。同一優先級的線路按分流方式分擔，便宜的不會把請求全拿走。優先級代表成本以外的考慮（質量、速度、信任的廠商）時選這個。
- **成本優先**：一個模型最便宜的線路先承接請求，不管優先級；更貴的只在所有更便宜的都不可用時才用，成本未知的排最後。有兩道門檻，免得便宜但不靠譜的線路只憑價格拿走流量：
  - **最低節省**（`SupplyCostMinSavingPercent`，預設 5%）：要比另一條便宜這麼多才排到它前面；差距更小算同價，按優先級和權重分擔。
  - **最低成功率**（`SupplyCostMinSuccessPercent`，預設 95%）：本小時和上一小時的成功率低於它的線路，按成本未知處理，排到運行正常的線路後面，恢復後再回到前面。請求不到 20 次的不判斷。

  更便宜的託管商也可能更慢或跑的是量化版，切換前先看一下這些線路。

模型的「線路」分頁會顯示請求實際的嘗試順序；只因為更貴而排在後面的備用線路標着 **更貴，僅兜底**，成功率不夠而沒能往前排的標着 **成功率低**。

### 網關裡的託管商（Vercel AI Gateway）

Vercel AI Gateway 上很多開源模型由多家託管商同時提供，價格和質量各不相同。不加指定時，Vercel 每次按自己的優先級和健康狀況挑一家，按那家的價格扣費，所以成本和實際由誰回答都說不準。對這類模型，同步價格時會讀出全部託管商，排出一個順序，每個請求都帶上（`providerOptions.gateway.order`）：

1. 廠商自營排第一（例如 Qwen 的阿里、GLM 的智譜）。
2. 其他託管商要先合格：正常服務、近一天可用率不低於**最低成功率**、沒有量化、上下文不短於模型標稱值、廠商支持快取時它也支持、價格不低於廠商價的 30%。合格的按價格從低到高排在後面。
3. **成本優先**時，比廠商便宜超過**最低節省**的合格託管商排到廠商前面。廠商暫停服務或可用率不夠時排到合格託管商後面。

排在前面的託管商不可用時，Vercel 照樣換下一家，請求不會因此失敗。渠道成本按順序裡第一家的價格算；價格詳情裡列出了這個順序。Vercel 沒有列出廠商自營的模型不加指定，按 Vercel 的列表價計成本。順序隨價格同步更新（啟動、每天、保存渠道時）。

Vercel 每個請求都會告訴我們實際由哪家託管商服務、扣了多少錢：託管商記在日誌詳情的**實際託管商**裡，扣費記作上游扣費。成本和毛利統計用這筆實際扣費（加渠道費率），不再按價格表估算，所以 Vercel 換到備用託管商時成本也是準的。

## 線路失敗時怎麼處理

怎麼處理看上游說了什麼，不只看「失敗了」：

| 發生了什麼 | 怎麼認出來 | 這一次請求 | 這條線路之後 |
|---|---|---|---|
| 請求本身被拒絕 | 針對請求的 400：請求體格式不對、參數不支持、上下文過長、內容被拒 | 直接返回給呼叫方，不換線路 | 不處理，也不拉低線路的成功率 |
| 餘額或額度用完 | 402、`insufficient_quota`、已知的「餘額不足」文案，或刷新餘額時發現已為 0 | 換到下一條線路 | 整個渠道暫停 30 分鐘，恢復前先測試，並通知管理員；刷新餘額發現有錢了就提前恢復 |
| 密鑰或賬號被拒 | 401、`invalid_api_key`、`account_deactivated`、命中禁用關鍵詞 | 換線路 | 整個渠道暫停 1 小時，恢復前先測試 |
| 這個渠道沒有這個模型 | 「model not found」一類的錯誤 | 換線路 | 只暫停這個渠道上的這個模型 |
| 限流或過載，並給了恢復時間 | 429、503 或 529，帶 `Retry-After`（或廠商自己的重置時間） | 換線路 | 這個渠道上的這個模型暫停到那個時間 |
| 限流，沒給時間 | 429 | 換線路 | 這個渠道上的這個模型按限流冷卻時間冷卻（預設 5 秒） |
| 上游出錯 | 500、502、503、504、連接中斷 | 換線路 | 一分鐘內第三次才暫停 2 分鐘，恢復前先測試 |
| 上游遲遲不回應 | 上游收下了請求，但一直沒有回應 | 還在重試時限內就換線路 | 立刻發一個測試請求；測試也失敗才暫停這個模型 |
| 已經開始輸出 | 串流響應發出一部分後中斷 | 不能換：呼叫方已經收到一部分內容 | 按上游出錯計數 |

把「這次請求失敗」和「這條線路不行了」分開，帶來兩條規則：

- **救一次請求的門檻低，給線路定性的門檻高。**失敗一次就可以換下一條線路。暫停一條線路，要麼上游明說了（餘額、密鑰、恢復時間），要麼失敗重複出現，要麼測試請求也失敗。上游遲遲不回應本身說明不了什麼，可能只是一個耗時長的請求碰上了正常的渠道，所以它不計數，只觸發一次測試。
- **會話留在提示快取所在的渠道。**打開會話親和後，一個會話的請求固定發往服務過它的渠道。這個渠道對其中一個請求返回上游錯誤時，會先在原渠道再發一次，仍失敗才換：這類錯誤多半一過就好，而換渠道要重新寫一次快取。重試次數設為 0 時不做這次額外嘗試。已經換走的會話留在新渠道，原渠道恢復後也不搬回去；新會話仍然從第一條線路開始。

表裏是內置的暫停規則，可以在 **閘道設定 → 容錯** 裏換成自己的。

## 價格閘

成本高於站點正常售價淨收入的線路，每接一個請求都虧錢。判斷線是：

> default 組倍率 ×（1 − 收款成本率）

判斷只比較輸入和輸出兩項成本。快取讀取不參與：它只是輸入的一部分，快取讀取價偏高的渠道，其餘輸入往往便宜得多，整個請求仍然賺錢。線路的價格詳情會把渠道的快取讀取成本和你的快取讀取售價並排列出，成本更高時給出提示，供你判斷那些以快取命中為主的線路。

設了利潤（判斷線高於 1）之後：高於這條線的新線路要等確認；已有的備用線路會關掉等確認；正在承接請求的不關，只通知管理員。**定價**卡片列出每個渠道的保本倍率、會虧的線路和每個用戶分組的淨收入。

折扣組不參與判斷：折扣是你自己的選擇。定價卡片仍會顯示每個分組下哪些渠道會虧。

## 用上游賬單核對價格

價格表可能錯在同步發現不了的地方：跟不上廠商調價、優惠結束了、中轉站在標價上加價。上游自己的賬單最準。Modeltaps 每小時把近三天上游實際扣費，和按價格表記下的預期成本（渠道標價，不含費率）做對比：

- **按模型**：用 OpenRouter、Vercel AI Gateway、Cheaper Inference 每個請求返回的費用。
- **按賬號**：用填了**上游管理密鑰**的 OpenAI、Anthropic、OpenRouter 渠道的每日賬單。賬單是整個賬號的，本站以外也在用這個賬號時會顯得偏高。

偏差 10% 以上、且至少 10 個請求和 0.10 美元時，渠道上會出現**上游扣費核對**提醒（平台管理 → **提醒**），並發一次價格變動通知。提醒連結到渠道的**統計**頁，那裡按模型、按天列出兩邊的金額。

- **扣得比預期多**：請求可能虧錢。改渠道價格、費率或成本倍率。
- **扣得比預期少**：成本設高了，價格閘可能誤擋線路。同樣去改。

費用重新對上後提醒自動關閉。Gemini 和 Vertex AI 暫時沒有可對比的賬單。

單條請求的成本可以在日誌詳情裡看（僅管理員）：渠道成本、它的來源（上游回報的實扣、渠道價格表、成本倍率或官方價），以及其中包含的渠道費率。上游事後才回報的實扣會取代當時的估算。成本未知的請求會如實標明，統計頁的每分鐘利潤不把它算進去。

## 官方調價日程

有些廠商會公佈某天起的新價，或者某天結束的優惠價。內置官方價帶着這些日期：到了那天價格自動切換（你改過或鎖定的不動），管理員收到**官方調價日程**提醒，並立刻重新拉取價格表，不用等到夜裡。

優惠價結束而廠商還沒公佈新價時，提醒會請你去核對廠商價格頁（附連結）。價格變了就手動改；提醒會一直保留，直到新版本寫入新價。

## 非高峰價

有的廠商在非高峰時段打折。DeepSeek 在週一至週五 01:00–04:00、06:00–10:00（UTC）以外收半價，內置官方價帶着這個時段，用戶在非高峰時段也按半價扣費。打折按請求開始的時間計，成本和上游扣費核對用同樣的口徑；日誌詳情裏會顯示「非高峰價」。

模型頁和價格表上顯示的仍是高峰價。DeepSeek 把中國法定假日也算作非高峰，Modeltaps 目前不認假日，這些日子按全價收：不會比廠商收得少。在模型價格的編輯頁可以點**一律按全價**，取消某個模型的非高峰折扣；鎖定的價格不會自動加上折扣。經其他渠道（如 OpenRouter）轉發時，成本按那個渠道自己的價格表計，不打折。

## 價格來源出問題時

渠道價格表和 models.dev 讀取失敗時，Modeltaps 保留上次讀到的價格，並在渠道的**模型**頁籤顯示失敗時間和原因。連續失敗兩次、並且持續 20 小時以上，就會出現**價格來源異常**提醒，同時發一次通知；下一次讀取成功後提醒自動關閉。只有開着自動同步的來源才會這樣提醒。

新讀到的列表如果比原來少了一半以上的模型，或者沒有價格的模型明顯變多（佔比多出 20 個百分點），多半是平台改了接口格式。這種列表不會寫入，原來的價格照常使用。如果平台確實下架了這麼多模型，在渠道的**模型**頁籤點**使用新列表**。

每天同步 models.dev 後，內置官方價會和 models.dev 上廠商自己的條目對比一次，輸入或輸出價相差 10% 以上的模型列在**內置官方價**提醒裏。這條提醒只是提示，不會改價：models.dev 自己也可能滯後或寫錯，請到廠商官網核對。DeepSeek 在 models.dev 上標的是非高峰價（五折），和內置價對得上就不算差異。

## 算例

### 1. 比官方價高 12% 賣

把 `default` 組倍率設成 **1.12**，收款成本率 **4%**。每 $1 目錄價淨收入 1.12 × 0.96 = **$1.0752**。

| 渠道 | 每 $1 目錄價的成本 | 毛利 |
|---|---|---|
| 官方 API | $1.00 | 7.5% |
| Vercel AI Gateway（3%） | $1.03 | 4.4% |
| Requesty（5%） | $1.05 | 2.4% |
| OpenRouter（5.5%） | $1.055 | 1.9% |

default 組用戶調用一個目錄價為每百萬 token $3 / $15 的模型，付 $3.36 / $16.80，不論哪個渠道承接。

### 2. 錄入一筆 Vercel 充值

你付了 **$103.00**，到賬 **$100.00** 額度。新增一條充值記錄：實付 103，到賬 100。渠道費率變成 3%，費率說明寫明是由充值記錄算出的。下一筆如果是 $206.40 充 $200，費率變成 (103 + 206.40) ÷ 300 − 1 = 3.13%。

### 3. 同一優先級的兩條線路

`glm-5.2` 有 Vercel（成本 ×1.03）和 Requesty（成本 ×1.05）兩條線路，優先級相同，負載均衡，權重 3 和 1。

- **優先級優先**：Vercel 承接約 75% 的請求，Requesty 約 25%。
- **成本優先**：兩者只差 2%，在最低節省 5% 以內，算同價，照樣按 75 / 25 分擔。最低節省設成 0 時，請求全部走 Vercel，只有 Vercel 暫停或出錯時才走 Requesty。

default 組用戶付的價格都一樣。

### 4. 成本優先，越過優先級

`gpt-5.1` 有 Requesty（最高優先級，成本 ×1.05）和低一檔的折扣中轉（成本 ×0.80）。

- **優先級優先**：Requesty 承接請求，中轉兜底。
- **成本優先**：中轉便宜 24%，承接請求，Requesty 兜底並標為更貴。中轉最近兩小時失敗了 10% 時，成功率低於 95%，Requesty 接回請求；中轉恢復後再排回前面。

### 5. 會虧錢的 VIP 折扣

`vip` 組倍率 **1.05**，收款成本率 4%，每 $1 淨收入 1.05 × 0.96 = $1.008。走官方 API 仍有 0.8% 毛利；走 Vercel（×1.03）虧 2.1%，走 Requesty 虧 4.0%。定價卡片的分組表會顯示 `vip` 下有幾個渠道會虧：提高倍率，或者把這部分虧損當作折扣的成本接受下來。
