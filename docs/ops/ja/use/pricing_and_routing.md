# 価格、コスト、供給の順番

このページでは、Modeltaps がユーザーの支払額、リクエストのコスト、リクエストを受ける供給をどう決めるかを説明します。各設定の場所と計算例も載せています。

## 3 つの数値

| 数値 | 内容 | 見える人 |
|---|---|---|
| **カタログ価格** | モデルの公式 API 価格（100 万トークンあたり、またはリクエスト・分あたり） | 全員（価格ページ） |
| **グループ倍率** | ユーザーグループごとにカタログ価格に掛ける倍率。`default` グループの倍率がサイトの通常価格です | ユーザーは自分のグループの価格を見ます |
| **チャネルコスト** | 上流があなたに請求する額：チャネルの表示価格 ×（1 + 手数料率） | 管理者のみ |

ユーザーが支払うのは常に **カタログ価格 × グループ倍率** です。リクエストを処理したチャネルによって変わりません。チャネルコストはユーザーに転嫁されず、どの供給がリクエストを受けるか、価格チェックがどの供給を止めるかだけを決めます。

リクエストあたりの粗利：

> カタログ価格 × グループ倍率 ×（1 − 決済コスト率）− チャネルコスト

**決済コスト率** は、あなたが代金を受け取るときにかかる割合（カード手数料、為替コスト）です。誰にも請求されず、コストと比べる純収入を下げるためだけに使います。

## 設定する場所

| 設定内容 | コンソールの場所 | 設定 / 項目 |
|---|---|---|
| カタログ価格 | **モデル** → モデル → 価格、または価格ソースから同期 | モデル価格 |
| サイトの利益 | **ユーザー → ユーザーグループ** → `default` グループ → 倍率（1.12 = 公式価格より 12% 高い） | `user_groups.ratio` |
| 割引・割増グループ | **ユーザー → ユーザーグループ** → その他のグループ | `user_groups.ratio` |
| 決済コスト率 | **プラットフォーム設定 → 課金 → 料金設定** → 決済コスト率 | `PaymentCostPercent` |
| 試算 | 同じカード：試す既定グループ倍率を入力（保存されません） | — |
| チャネルの表示価格 | **チャネル** → チャネル → 価格（上流から同期）。価格表のない中継：詳細 → コスト倍率 | `channel_prices`、`cost_ratio` |
| チャネル手数料率 | **チャネル** → チャネル → 詳細 → 手数料率、またはチャージ記録 | `fee_rate`、`fee_note` |
| 呼び出し順序 | **プロバイダー**ページ：チャネルをドラッグして段に並べ、同じ段のチャネルは比率で分担します。個別のモデルは「供給」タブで独自に設定 | 割り当てポリシー、供給の優先度と重み |
| 順序の基準 | **プロバイダー**ページの上部、または **プラットフォーム設定 → 供給の割り当て → 供給による振り分けと順序の基準** | `SupplyCostOrder` |

上記の各設定の型、範囲、その他の例は [設定リファレンス](../settings/index.md) にあります。AI アシスタントは [管理 MCP](./admin_mcp.md) で調べられます。

## チャネル手数料率

手数料率は、プロバイダーが表示価格とは別に請求する割合です。多くのプロバイダーはクレジット購入時に請求するので：

> 手数料率 = 支払った現金 ÷ 受け取ったクレジット − 1

新しいチャネルは、プロバイダーが公表している手数料率から始まります。公表されていない場合は、決済画面で確認した手数料率を使います：

| プロバイダー | 既定 | 出典 |
|---|---|---|
| Requesty | 5% | 課金ドキュメントのチャージ手数料 |
| OpenRouter | 5.5% | FAQ のクレジット購入手数料（最低 $0.80、暗号資産 5%） |
| Vercel AI Gateway | 3% | Vercel のドキュメントには記載がなく、決済手数料は購入者負担とだけあります。2026-11-18 の決済画面では $100 のクレジットに $3.00 の手数料 |
| 公式ベンダー API、その他の中継 | 0% | — |

**チャネル → 詳細 → チャージ記録** に実際のチャージを記録します。支払った現金（カード・為替手数料込み）と受け取ったクレジットです。以後、手数料率は直近 10 件のチャージから算出され、既定値を置き換えます。ボーナスクレジットで手数料率が負になることはありません。

## どの供給がリクエストを受けるか

1. 呼び出し順序（プロバイダーページ、または個別に設定したモデル自身の数値）で供給を段に分けます。
2. 順序の基準が**コスト優先**のときは、コストでも並べます（下記）。
3. 同じ段の供給は重みでリクエストを分担します。予備だけにしたい供給は下の段に置きます。

**順序の基準**（`SupplyCostOrder`）は、コストを順序に使うかどうかを決めます：

- **呼び出し順序優先**（既定）：コストは順序に影響しません。同じ段の供給は重みで分担し、安い供給がすべてを取ることはありません。順序がコスト以外の事情（品質、速度、信頼できる提供元）を表すときに選びます。
- **コスト優先**：呼び出し順序に関係なく、モデルの最安の供給が先にリクエストを受けます。高い供給は、より安い供給がすべて使えないときだけ使われ、コスト不明の供給は最後です。安いが不安定な供給が価格だけでトラフィックを取らないよう、2 つの条件があります：
  - **最低節約率**（`SupplyCostMinSavingPercent`、既定 5%）：別の供給より前に出るには、これだけ安い必要があります。差がこれ以内なら同じコストとみなし、優先度と重みで分担します。
  - **最低成功率**（`SupplyCostMinSuccessPercent`、既定 95%）：現在と直前の 1 時間の成功率がこれを下回る供給は、コスト不明として扱われ、正常な供給の後ろに回り、回復すると前に戻ります。試行が 20 回未満の供給は判定しません。

  安いホストは遅かったり量子化モデルだったりすることもあるので、切り替える前に供給を確認してください。

モデルの「供給」タブに、リクエストが試す順序が表示されます。高いという理由だけで後ろにいる予備の供給には **高い・予備のみ**、成功率が足りずに前に出られない安い供給には **成功率が低い** と表示されます。

### ゲートウェイ内のホスト（Vercel AI Gateway）

Vercel AI Gateway の多くのオープンモデルは、価格も品質も異なる複数のホストが提供しています。指定しないと、Vercel はリクエストごとに独自の優先度と最近の状態でホストを選び、そのホストの価格で課金するため、コストも実際に応答するホストも事前にはわかりません。こうしたモデルについては、価格同期の際にすべてのホストを読み込んで順序を決め、各リクエストにその順序（`providerOptions.gateway.order`）を付けます：

1. ベンダー自身のホストが先頭（Qwen なら Alibaba、GLM なら Z.ai）。
2. ほかのホストは条件を満たす必要があります：稼働中、直近 1 日の稼働率が**最低成功率**以上、量子化なし、コンテキストがモデルの公称値以上、ベンダーがキャッシュに対応していればそのホストも対応、価格がベンダーの 30% 以上。条件を満たすホストが安い順に続きます。
3. **コスト優先**では、ベンダーより**最低節約率**以上安い条件を満たすホストがベンダーの前に出ます。ベンダーが停止中か稼働率不足なら、条件を満たすホストの後ろに回ります。

前のホストが使えないときも Vercel は次のホストに移るため、それでリクエストが失敗することはありません。チャネルのコストは先頭ホストの価格で、価格の詳細に順序が表示されます。Vercel がベンダー自身のホストを載せていないモデルは指定せず、Vercel の掲載価格でコストを計算します。順序は価格と一緒に更新されます（起動時、毎日、チャネル保存時）。

Vercel はリクエストごとに、実際に応答したホストと課金額を返します。ホストはログ詳細の**実際のホスト**に、課金額は上流の課金額として記録されます。コストと粗利の集計はこの実際の課金額（チャネル手数料込み）を使い、価格表からの見積もりは使わないため、Vercel が予備のホストに切り替えたときもコストは正確です。

## 供給が失敗したとき

失敗したという事実だけでなく、上流が何を返したかで扱いが決まります。

| 起きたこと | 見分け方 | このリクエスト | その後の供給 |
|---|---|---|---|
| リクエスト自体が拒否された | リクエストに関する 400：本文の形式が不正、未対応のパラメータ、コンテキストが長すぎる、内容が拒否された | 呼び出し元にそのまま返し、他の供給では試さない | 何もしない。供給の成功率も下げない |
| 残高またはクォータ切れ | 402、`insufficient_quota`、既知の「残高不足」メッセージ、または残高更新で残高ゼロと分かったとき | 次の供給へ移る | チャネル全体を 30 分間一時停止し、再開前にテストして、管理者に通知する。残高更新で残高が見つかれば早めに再開する |
| キーまたはアカウントが拒否された | 401、`invalid_api_key`、`account_deactivated`、無効化キーワードに一致 | 移る | チャネル全体を 1 時間一時停止し、再開前にテストする |
| そのチャネルにモデルがない | 「model not found」などのエラー | 移る | そのチャネルのそのモデルだけを一時停止する |
| レート制限または過負荷で、再開時刻が示された | 429、503、529 に `Retry-After`（またはプロバイダ独自のリセット時刻）が付く | 移る | そのチャネルのそのモデルをその時刻まで一時停止する |
| レート制限で、時刻が示されない | 429 | 移る | そのチャネルのそのモデルをレート制限のクールダウン（既定で 5 秒）のあいだ外す |
| 上流のエラー | 500、502、503、504、接続の切断 | 移る | 1 分間に 3 回目で初めて 2 分間一時停止し、再開前にテストする |
| 時間内に応答がない | 上流がリクエストを受け取ったまま応答しない | リトライの時間制限内なら移る | すぐにテストリクエストを送り、それも失敗したときだけそのモデルを一時停止する |
| 応答がすでに始まっていた | ストリームが最初のデータの後で途切れた | 移れない：呼び出し元は応答の一部を受け取っている | 上流のエラーとして数える |

「このリクエストが失敗した」ことと「この供給が使えない」ことを分けて扱うので、次の 2 点が成り立ちます。

- **リクエストを救う基準は低く、供給を判定する基準は高い。**1 回の失敗で次の供給を試します。供給を一時停止するのは、上流がそう伝えたとき（残高、キー、再開時刻）、失敗が繰り返されたとき、またはテストリクエストも失敗したときです。時間内に応答がなかっただけでは何も分かりません。正常なチャネルで時間のかかるリクエストだっただけかもしれないので、回数には数えず、テストで確かめるだけです。
- **セッションはプロンプトキャッシュのあるチャネルに留まる。**セッションアフィニティが有効なとき、セッションのリクエストはそれを処理したチャネルへ送られます。そのチャネルが上流のエラーを返した場合は、移る前に同じチャネルへもう一度送ります。この種のエラーは一時的なことが多く、別のチャネルではキャッシュを書き直すことになるためです。リトライ回数が 0 のときは、この追加の試行は行いません。移ったセッションは、元のチャネルが戻ったあとも新しいチャネルに留まり、新しいセッションはまた最初の供給から始まります。

表は組み込みの一時停止ルールです。**ゲートウェイ設定 → 耐障害性** で独自のルールに置き換えられます。

## 価格チェック

サイトの通常価格による純収入よりコストが高い供給は、リクエストを受けるたびに損失が出ます。判定ラインは：

> default グループ倍率 ×（1 − 決済コスト率）

判定で比べるのは入力と出力のコストだけです。キャッシュ読み取りは対象外です。キャッシュ読み取りは入力の一部にすぎず、その単価が高めのチャネルでも残りの入力がずっと安いことが多く、リクエスト全体では利益が出ます。供給の価格詳細には、チャネルのキャッシュ読み取りコストと販売価格が並んで表示され、コストのほうが高い場合はその旨が示されるので、キャッシュヒットが中心の供給を判断する材料になります。

利益を設定すると（判定ラインが 1 を超えると）、ラインを超える新しい供給は確認待ちになり、既存の予備も確認待ちとして無効になります。リクエストを受けている供給は止めず、管理者に通知します。**料金設定** カードには、各チャネルの損益分岐倍率、損失が出る供給、各ユーザーグループの純収入が表示されます。

割引グループは判定に使いません。割引はあなた自身の選択だからです。それでも料金設定カードには、各グループでどのチャネルが損失になるかが表示されます。

## 上流の請求額で価格を確かめる

価格表は、同期では気づけない形で間違うことがあります。ベンダーの改定に追いついていない、プロモーションが終わった、中継サービスが表示価格に上乗せしている、などです。確かなのは上流自身の請求額です。Modeltaps は 1 時間ごとに、過去 3 日間の上流の実際の請求額と、価格表から記録した想定原価（チャネルの表示価格、手数料を除く）を比べます。

- **モデルごと**：OpenRouter、Vercel AI Gateway、Cheaper Inference がリクエストごとに返す費用を使います。
- **アカウントごと**：**上流の管理キー**を設定した OpenAI、Anthropic、OpenRouter チャネルの日次請求額を使います。請求額はアカウント全体のもので、このサイト以外でも同じアカウントを使っていると高めに見えます。

差が 10% 以上で、リクエストが 10 件以上かつ 0.10 ドル以上あると、チャネルに**上流の請求額チェック**のアラートが開き（プラットフォーム管理 → **アラート**）、価格変更の通知が一度送られます。アラートからチャネルの**統計**タブに移動でき、モデル別・日別に両方の金額を確認できます。

- **想定より多く請求された**：リクエストが赤字の可能性があります。チャネルの価格、手数料率、原価倍率を直してください。
- **想定より少なく請求された**：原価が高すぎる設定で、価格チェックで供給が不要に保留されることがあります。同じように直してください。

費用が再び一致するとアラートは自動で閉じます。Gemini と Vertex AI には、まだ比べられる請求データがありません。

リクエスト単位のコストは、ログの詳細で確認できます（管理者のみ）。チャネルコスト、その出どころ（上流が報告した課金額、チャネルの価格表、コスト倍率、公式価格）、そこに含まれるチャネル手数料率が表示されます。上流がリクエストの後で報告した課金額は、それまでの見積もりを置き換えます。コストが不明なリクエストはその旨が表示され、統計ページの 1 分あたりの利益には含まれません。

## 公式価格の改定日程

ベンダーによっては、ある日から始まる新価格や、ある日に終わる導入価格を公表します。組み込みの公式価格はこれらの日付を持っています。当日になると価格は自動で切り替わり（編集・固定した価格はそのまま）、管理者には**公式価格の改定日程**のアラートが届き、価格表は夜間を待たずにすぐ再取得されます。

導入価格が終わってもベンダーが次の価格を公表していない場合は、アラートがベンダーの価格ページ（リンク付き）の確認を促します。価格が変わっていれば手動で設定してください。新しい価格を含むリリースが出るまで、アラートは開いたままです。

## オフピーク価格

オフピーク時間に値引きするベンダーがあります。DeepSeek は月〜金の 01:00–04:00 と 06:00–10:00（UTC）以外を半額にしており、組み込みの公式価格にこの時間帯が入っているので、ユーザーもオフピーク時間は半額で請求されます。値引きはリクエストの開始時刻で判断し、コストと上流の請求額チェックも同じ基準です。ログの詳細には「オフピーク価格」と表示されます。

モデルページと価格表には引き続きピーク価格を表示します。DeepSeek は中国の祝日もオフピークとしていますが、Modeltaps はまだ祝日を扱わないため、その日は通常価格で請求します（ベンダーより安くなることはありません）。モデル価格の編集画面で**常に通常価格**を押すと、そのモデルのオフピーク値引きを外せます。ロックした価格に値引きが自動で付くことはありません。ほかのチャネル（OpenRouter など）を経由する場合、コストはそのチャネル自身の価格表で計算し、値引きしません。

## 価格ソースに問題があるとき

チャネルの価格表や models.dev を読み込めないとき、Modeltaps は最後に読み込んだ価格をそのまま使い、失敗し始めた時刻と理由をチャネルの**モデル**タブに表示します。20 時間以上にわたって 2 回続けて失敗すると**価格ソースの異常**アラートが開き、通知が 1 回送られます。次に読み込めればアラートは自動で閉じます。対象は自動同期で読み込むソースだけです。

新しい一覧でモデルが半分以上減った場合や、価格のないモデルの割合が 20 ポイント以上増えた場合は、たいていプラットフォーム側の形式変更です。この一覧は保存せず、保存済みの価格を使い続けます。本当にそれだけのモデルが削除されたときは、チャネルの**モデル**タブで**新しい一覧を使う**を押してください。

毎日の models.dev 同期のあと、組み込みの公式価格をそこにあるベンダー自身の項目と比べます。入力か出力の価格が 10% 以上違うモデルは**組み込みの公式価格**アラートに並びます。価格は変えません。models.dev も遅れたり誤ったりするので、ベンダーの価格ページで確認してください。DeepSeek の models.dev の項目はオフピーク価格（通常の半額）なので、それと一致すれば差異とはみなしません。

## 計算例

### 1. 公式価格より 12% 高く売る

`default` グループの倍率を **1.12**、決済コスト率を **4%** にします。カタログ価格 $1 あたりの純収入は 1.12 × 0.96 = **$1.0752** です。

| チャネル | カタログ価格 $1 あたりのコスト | 粗利 |
|---|---|---|
| 公式 API | $1.00 | 7.5% |
| Vercel AI Gateway（3%） | $1.03 | 4.4% |
| Requesty（5%） | $1.05 | 2.4% |
| OpenRouter（5.5%） | $1.055 | 1.9% |

default グループのユーザーが 100 万トークンあたり $3 / $15 のモデルを呼ぶと、どのチャネルが処理しても $3.36 / $16.80 を支払います。

### 2. Vercel のチャージを記録する

**$103.00** を支払い、**$100.00** の AI クレジットを受け取りました。支払い 103、受け取り 100 でチャージ記録を追加すると、手数料率は 3% になり、メモにはチャージ記録から算出したことが書かれます。次のチャージが $206.40 で $200 なら、手数料率は (103 + 206.40) ÷ 300 − 1 = 3.13% になります。

### 3. 同じ優先度の 2 つの供給

`glm-5.2` の供給は Vercel（コスト ×1.03）と Requesty（コスト ×1.05）で、同じ段にあり、重みは 3 と 1 です。

- **呼び出し順序優先**：Vercel が約 75%、Requesty が約 25% を受けます。
- **コスト優先**：差は 2% で最低節約率 5% 以内なので同じコスト扱いになり、やはり 75 / 25 で分担します。最低節約率を 0 にすると、すべて Vercel に行き、Requesty は Vercel が一時停止中か失敗しているときだけ使われます。

default グループのユーザーの支払いはどちらでも同じです。

### 4. 段を超えてコスト優先

`gpt-5.1` の供給は、1 段目の Requesty（コスト ×1.05）と、2 段目の割引中継（コスト ×0.80）です。

- **呼び出し順序優先**：Requesty がリクエストを受け、中継は予備です。
- **コスト優先**：中継は 24% 安いのでリクエストを受け、Requesty は「高い」と表示された予備になります。中継が直近 2 時間で 10% 失敗すると成功率 95% を下回り、中継が回復するまで Requesty がリクエストを引き継ぎます。

### 5. 損失が出る VIP 割引

`vip` グループの倍率 **1.05**、決済コスト率 4% では、$1 あたりの純収入は 1.05 × 0.96 = $1.008 です。公式 API 経由ならまだ 0.8% の粗利がありますが、Vercel（×1.03）経由では 2.1%、Requesty 経由では 4.0% の損失です。料金設定カードのグループ表に、`vip` で損失になるチャネルの数が表示されます。倍率を上げるか、割引のコストとして受け入れてください。
