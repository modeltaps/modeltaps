# デプロイ手順

::: warning データベースの独立性
Modeltaps は独自のデータベース構造を使用します。専用のデータベースを用意し、他のサービスと同じテーブル群を共用しないでください。
:::

## 設定方法

システムは次の 2 種類の設定方法に対応しています。

1. 環境変数
2. 設定ファイル（config.yaml）

::: tip 設定の優先順位
環境変数 > 設定ファイル
:::

### 必須の設定

- `USER_TOKEN_SECRET`: 必須。ユーザートークンを生成するための秘密鍵で、32 文字を超える長さが必要です。設定後は変更しないでください。変更すると発行済みのユーザートークンが無効になります
- `SESSION_SECRET`: 設定を推奨します。ユーザーのログイン状態を維持するために使用します。未設定の場合、再起動のたびにログイン済みユーザーは再ログインが必要になります

いずれもそれぞれ異なる強いランダム値を生成してください。

```bash
openssl rand -base64 48 | tr -d '\n'; echo
```

::: danger ドキュメント内のサンプル値をそのまま使用しないでください
本ページに登場する秘密鍵、パスワード、データベース接続文字列は**すべてプレースホルダー**（`<...>` の形式）であり、書式を示すためのものです。**本番環境では使用できません**。実際の値はホスト上の `.env` ファイル（`chmod 600` を実行）または秘密情報管理サービスに保存し、コマンドライン引数や `docker-compose.yml` に直接書き込んだり、リポジトリにコミットしたりしないでください。
:::

## プライベートイメージレジストリへのログイン

Modeltaps のイメージはプライベートイメージレジストリ `ghcr.io/modeltaps/modeltaps` で公開されています。取得前に**必ずログイン**してください。ログインしていないと、以下の `docker pull` / `docker run` / `docker-compose up` は権限不足で失敗します。

::: tip 権限について
このイメージレジストリはアクセス制御が有効になっており、許可されたアカウントのみが取得できます。ログイン後も取得できない場合は、提供元に対象アカウントへの読み取り専用権限の付与を依頼してください。
:::

1. **アクセストークンを準備する**

   `read:packages`（パッケージの読み取り専用取得）権限を持つアクセストークンを使用し、余分な権限は付与しないでください。

   ::: warning GHCR はクラシック PAT のみ受け付けます
   GitHub Container Registry は**クラシック（classic）Personal Access Token** のみを受け付けます。ファイングレインド（fine-grained）トークンは Packages 権限を扱えないため、ログインしても `unauthorized` のままです。
   :::

2. **ログイン（stdin 方式）**

   ```shell
   echo "$CR_PAT" | docker login ghcr.io -u <USERNAME> --password-stdin
   ```

   ::: warning トークンを漏洩させないでください
   トークンは環境変数または標準入力経由で `docker login` に渡してください。コマンドライン引数、スクリプト、平文ファイルに書き込まないでください（shell の履歴やプロセス一覧に残ります）。例の `$CR_PAT` はローカルで安全に設定した環境変数から取得し、`<USERNAME>` は実際のアカウント名に置き換えてください。
   :::

3. **取得を検証する**

   ```shell
   docker pull ghcr.io/modeltaps/modeltaps:latest
   ```

   取得に成功すればログインは有効です。

   ::: warning 認証情報はログインした OS ユーザーのものです
   `docker login` の認証情報は、**実行した OS ユーザー**の `~/.docker/config.json` に保存され、ユーザー間で共有されません。**実際に `docker compose` を実行するユーザー**でログインしてください。`sudo docker compose` を使う場合は `sudo docker login ghcr.io` も実行し（認証情報は root の `/root/.docker/config.json` に保存されます）、そうしないと取得は `unauthorized` で失敗し続けます。
   :::

## Docker でのデプロイ

### 事前準備

1. データディレクトリを作成します。

```bash
# メインのデータディレクトリを作成
sudo mkdir -p /data/modeltaps
cd /data/modeltaps
```

::: tip データディレクトリの権限を強化する
このディレクトリには SQLite データベース、秘密情報を含むファイル、ログが置かれます。`modeltaps.db` はアプリケーションによって `0644` の権限で作成されるため、ディレクトリ自体が他のユーザーに開いていると、ホスト上の誰でもデータベースを読み取れます。`.env` / `config.yaml` を書き終えたら、コンテナを起動する前にディレクトリの所有者をコンテナ内のユーザー（UID 10001）に変更し、所有者のみがアクセスできるようにしてください。

```bash
sudo chown -R 10001:10001 /data/modeltaps
sudo chmod 700 /data/modeltaps
```

詳しい手順は [ディレクトリ権限の強化](#ディレクトリ権限の強化) を参照してください。
:::

2. Docker が正しくインストールされ、起動していることを確認します。

```bash
# Docker の状態を確認
sudo systemctl status docker
# 起動していない場合は Docker を起動
sudo systemctl start docker
```

::: warning 注意

- `-p 3000:3000` の最初の `3000` はホスト側のポートで、必要に応じて変更できます。
- データとログはホストの `/data/modeltaps` ディレクトリに保存されます。このディレクトリが存在し書き込み権限があることを確認するか、適切なディレクトリに変更してください。このディレクトリには SQLite データベースとログファイルが含まれ機密データに当たるため、[ディレクトリ権限の強化](#ディレクトリ権限の強化) に従って所有者と権限を設定してください。
- 起動に失敗する場合は `--privileged=true` を追加してください。
- 同時接続数が多い場合は、**必ず** `SQL_DSN` を設定してください。
  :::

### 環境変数を使ったデプロイ

環境変数の詳細は [環境変数](./env.md) を参照してください。

秘密鍵はまずホストの `.env` ファイルに書き込み、`--env-file` でコンテナに注入することを推奨します。こうすることで秘密鍵が shell の履歴やプロセス一覧に残りません。

```bash
# /data/modeltaps/.env —— 以下の山かっこ内はすべてプレースホルダーです。自分で生成した値に置き換えてください
TZ=UTC
USER_TOKEN_SECRET=<openssl rand -base64 48 で生成したランダム値>
SESSION_SECRET=<別途生成したランダム値>
```

作成後はファイル権限を強化し、所有者のみ読み書きできるようにします。

```bash
chmod 600 /data/modeltaps/.env
```

#### SQLite を使う場合

```shell
docker run -d -p 3000:3000 \
  --name modeltaps \
  --restart always \
  --env-file /data/modeltaps/.env \
  -v /data/modeltaps:/data \
  ghcr.io/modeltaps/modeltaps:latest
```

#### MySQL を使う場合

`.env` に `SQL_DSN` を追記します。コンテナの起動コマンドは SQLite の場合と完全に同じです。

```bash
SQL_DSN=<DB_USER>:<DB_PASSWORD>@tcp(<DB_HOST>:3306)/modeltaps
```

#### PostgreSQL を使う場合

```bash
SQL_DSN=postgres://<DB_USER>:<DB_PASSWORD>@<DB_HOST>:5432/modeltaps
```

::: warning データベースアカウント
Modeltaps 専用のデータベースアカウントを作成し、強力なパスワードを設定してください。`root` などのスーパーユーザーアカウントを流用しないでください。
:::

デプロイ完了後、`http://localhost:3000` にアクセスしてください。初回ログイン後は、まず [サーバーアドレスを設定](#サーバーアドレスの設定) してください。

### 設定ファイルを使ったデプロイ

1. 設定ファイルのテンプレートを準備します。設定ファイルの例 `config.example.yaml` は配布パッケージに同梱されています（パッケージのルートにあります）。これをデータディレクトリにコピーし、`config.yaml` にリネームします。

```bash
cd /data/modeltaps
cp <配布パッケージのディレクトリ>/config.example.yaml ./config.yaml
```

2. 必要に応じて設定ファイルの内容を変更します。よく使う設定項目は次のとおりです。

```yaml
# 必須の設定（山かっこ内はプレースホルダーです。自分で生成した強いランダム値に置き換えてください。本番環境では使用しないでください）
user_token_secret: "<openssl rand -base64 48 で生成したランダム値>" # ユーザートークンの秘密鍵
session_secret: "<別途生成したランダム値>" # セッションの秘密鍵

# データベース設定
sql_dsn: "<DB_USER>:<DB_PASSWORD>@tcp(<DB_HOST>:3306)/modeltaps" # MySQL の設定例
```

::: warning 設定ファイルには平文の秘密鍵が含まれます
`config.yaml` は秘密鍵を平文で保存します。`chmod 600 config.yaml` を実行して権限を強化し、リポジトリにコミットされないようにしてください。秘密鍵をディスクに保存したくない場合は、前節の `.env` + 環境変数方式を利用してください。
:::

3. コンテナを実行します

```shell
docker run -d -p 3000:3000 \
  --name modeltaps \
  --restart always \
  -e TZ=UTC \
  -v /data/modeltaps:/data \
  ghcr.io/modeltaps/modeltaps:latest
```

## Docker Compose でのデプロイ

::: warning 先にプライベートイメージレジストリへログインしてください
プライベートイメージを利用するには [プライベートイメージレジストリへのログイン](#プライベートイメージレジストリへのログイン) を先に済ませる必要があります。ログインしていないと `docker-compose up` でのイメージ取得が失敗します。
:::

### 事前準備

1. 必要なディレクトリ構成を作成します。

```bash
# メインディレクトリを作成
sudo mkdir -p /data/modeltaps
cd /data/modeltaps
# サブディレクトリを作成
mkdir data
```

::: tip データディレクトリの権限を強化する
`data` サブディレクトリはコンテナ内の `/data` としてマウントされ、SQLite データベース、設定ファイル、ログが置かれます。`modeltaps.db` はアプリケーションによって `0644` の権限で作成されるため、ディレクトリが他のユーザーに開いていると、ホスト上の誰でもデータベースを読み取れます。**初回起動の前に**、所有者をコンテナ内のユーザー（UID 10001）に変更し、所有者のみがアクセスできるようにしてください。

```bash
sudo chown -R 10001:10001 data
sudo chmod 700 data
```

詳しい手順は [ディレクトリ権限の強化](#ディレクトリ権限の強化) を参照してください。
:::

2. オーケストレーションファイルと環境変数テンプレートを準備します。`docker-compose.yml` と `.env.example` は配布パッケージのルートにあります。これらをカレントディレクトリにコピーし、環境変数テンプレートは `.env` として保存します。

```bash
cp <配布パッケージのディレクトリ>/docker-compose.yml ./
cp <配布パッケージのディレクトリ>/.env.example ./.env
```

3. `.env` を編集して秘密鍵を記入します。`docker-compose.yml` 内の秘密鍵を直接変更**しないでください**。

`docker-compose.yml` の秘密鍵はすべて `${VAR:?...}` の形式で書かれており、同じディレクトリの `.env` から自動的に読み込まれます。いずれかが欠けている場合、`docker-compose up` はエラーで終了します。少なくとも `SESSION_SECRET`、`USER_TOKEN_SECRET`、`MYSQL_PASSWORD`、`MYSQL_ROOT_PASSWORD` を記入する必要があります。値は次のコマンドで生成してください。

```bash
# セッションとトークンの秘密鍵
openssl rand -base64 48 | tr -d '\n'; echo
# データベースのパスワード
openssl rand -base64 24 | tr -d '\n'; echo
```

作成後はファイル権限を強化します。

```bash
chmod 600 .env
```

::: warning .env をコミットしないでください
`.env` には平文の秘密鍵が含まれます。`.gitignore` で除外されていることを確認し、デプロイパッケージと一緒に配布しないでください。
:::

設定ファイル方式に切り替える場合は、以下のコマンドを実行し、`docker-compose.yml` 内の `SQL_DSN` / `REDIS_CONN_STRING` / `SESSION_SECRET` / `USER_TOKEN_SECRET` パラメータを削除してください。

```shell
# アプリケーション設定ファイルのテンプレートをコピー
cp <配布パッケージのディレクトリ>/config.example.yaml ./data/config.yaml
```

### サービスの起動

```shell
docker-compose up -d
```

サービスを起動したら、以下のコマンドでデプロイ状況を確認できます。

```shell
docker-compose ps
```

すべてのサービスが正常に起動し、状態が 'Up' になっていることを確認してください。

デプロイ完了後、`http://localhost:3000` にアクセスしてください。初回ログイン後は、まず [サーバーアドレスを設定](#サーバーアドレスの設定) してください。

### 任意：ローカルのドキュメントサイトも起動する

`docker-compose.yml` には既定では**起動しない** `docs` サービスも含まれており、社内ネットワークやオフライン環境で本ドキュメントサイトを自前で構築するために使用します。profile で制御されているため、通常の `docker-compose up -d` には一切影響しません。

```shell
docker compose --profile docs up -d
```

起動後は `http://localhost:3001` にアクセスしてください（`/llms.txt`、`/llms-full.txt` も併せて提供されます）。

::: warning 完全な配布パッケージが必要です
このサービスはイメージの取得ではなくローカルビルド（ビルドコンテキストは配布パッケージ内の `docs/` ディレクトリ）で動作するため、完全な配布パッケージを持つマシンでのみ利用できます。`docker-compose.yml` だけを取得した場合は起動できません。初回ビルドではドキュメントサイトの依存関係をインストールするためにインターネット接続が必要です。
:::

ドキュメントサイトのみ停止し、ゲートウェイサービスを維持する場合は次のとおりです。

```shell
docker compose --profile docs stop docs
```

## 手動デプロイ

コンテナイメージ以外にも、配布パッケージには各プラットフォーム向けの `modeltaps` 実行ファイルが含まれており、ホスト上で直接実行できます。

1. **実行ファイルを配置する**：配布パッケージ内の `modeltaps` 実行ファイルをインストールディレクトリ（例：`/opt/modeltaps`）にコピーします。

2. **アプリケーションを実行する**：実行権限を付与して実行します。

   ```shell
   chmod u+x modeltaps
   ./modeltaps --port 3000 --log-dir ./logs
   ```

3. **アプリケーションにアクセスする**：ブラウザで `http://localhost:3000` にアクセスしてログインします。初期アカウントのユーザー名は `root` で、初期パスワードは初回起動時の設定によって決まります。

   - `ROOT_PASSWORD` を設定した場合（長さ 8〜64 文字）：その値が root の初期パスワードになります。長さが要件を満たさない場合、プログラムは起動に失敗します。
   - `ROOT_PASSWORD` を設定しない場合：プログラムが `crypto/rand` で 16 文字の強いランダムパスワードを生成し、**初回起動時のログに 1 度だけ出力**します。形式は次のとおりです。

     ```text
     no user exists, create a root user for you: username is root, initial root password: <ランダムパスワード>
     ```

   ローカル開発の取り決め：`ROOT_PASSWORD=root` と `ROOT_PASSWORD_ALLOW_INSECURE=true` を設定すると、初回起動後に `root/root` でログインできます。このスイッチはローカル開発専用で、本番環境では絶対に有効化しないでください。

   ::: warning 初期パスワード
   この処理はデータベースにまだユーザーが存在しない場合にのみ有効です。初回ログイン後は直ちに root のパスワードを変更し、初期パスワードを含む起動ログを削除してください（[ディレクトリ権限の強化](#ディレクトリ権限の強化) を参照）。
   :::

実行方法と設定項目はコンテナデプロイと同じです。`.env` / 環境変数で注入することも、`--config ./config.yaml` で設定ファイルを指定することもできます（[コマンドライン引数](./cli.md) を参照）。本番環境では [ベアメタル（手動）デプロイ](#ベアメタル-手動-デプロイ) に従ってディレクトリとファイルの権限を強化してください。

## サーバーアドレスの設定

サーバーアドレスの出荷時の初期値は `http://localhost:3000` です。サイトを別のドメイン、IP アドレス、ポートで公開する場合（リバースプロキシ経由を含む）は、初回ログイン直後に変更してください。

1. root または管理者アカウントでログインし、「システム設定 → サイト」を開いて「サーバー設定」カードを探します。
2. 「サーバーアドレス」に、ユーザーが実際にサイトへアクセスする完全なアドレスを入力します。スキームを含め、既定以外のポートも記載してください（例：`https://yourdomain.com`）。
3. 「保存」をクリックします。

バックエンドはこのアドレスを使って外部向けのリンクをすべて組み立てます。初期値のままだと、以下はすべて `localhost` を指し、ユーザーは利用できません。

- 「API キー」ページに表示される Base URL とサンプルコマンド
- パスワード再設定などのメール内リンク
- OAuth / OIDC ログインのコールバックと支払いコールバック
- パスキー（WebAuthn）が紐づくサイトのドメイン

初期値のままの間は、このカードに警告が表示され、現在ブラウザでアクセスしているアドレスが推奨値として示されます。

::: warning パスキーを登録する前にアドレスを設定する
パスキーは登録時のサーバーアドレスのドメインに紐づくため、後からドメインを変更すると登録済みのパスキーは使えなくなります。先にサーバーアドレスを設定してサービスを一度再起動し、そのうえで [管理者の緊急ログイン経路](#管理者の緊急ログイン経路) に従って root のパスキーを登録してください。
:::

## ディレクトリ権限の強化

ログディレクトリとデータディレクトリはいずれも機密情報をディスクに書き出します。既定の権限では同一マシン上の他ユーザーによる読み取りを防ぐには**不十分**なため、デプロイ後に手動で強化してください。

### なぜ強化が必要か

**1. ログディレクトリに root の初期パスワードが記録される**

初回起動時（データベースにまだユーザーが存在しない場合）、`ROOT_PASSWORD` が未設定であればプログラムは 16 文字のランダムパスワードを生成し、**平文で 1 度出力**します。

```text
no user exists, create a root user for you: username is root, initial root password: <ランダムパスワード>
```

このログは同時に 2 か所に書き込まれます。

- **ログファイル**：パスは `LOG_DIR` / `LOGS_FILENAME`（既定は `./logs` / `modeltaps.log`。[環境変数](./env.md)、[コマンドライン引数](./cli.md) を参照）です。コンテナイメージの作業ディレクトリは `/data` のため、既定では `/data/logs/modeltaps.log`、つまりホストのマウントポイント配下の `logs/modeltaps.log` になります。
- **プロセスの標準エラー出力**：`docker logs modeltaps` や systemd journal で確認できる出力です。

権限の現状について、次の 2 点に注意してください。

- ログディレクトリが存在しない場合はプログラムが自ら作成します。作成時に要求する権限は `0777`（実際の値は umask の影響を受け、通常は `0755`）であり、**同一マシンの他ユーザーが入って読み取れます**。
- ログファイルは lumberjack が新規作成する際は `0600` ですが、ローテーション時には**既存ファイルの権限を引き継ぎます**。事前に緩い権限の `modeltaps.log` を手動で作成していた場合、その緩い権限がずっと継承され続けます。

**2. データディレクトリにデータベースと平文の設定が含まれる**

マウントポイント（例では `/data/modeltaps`）配下には通常、次のものが含まれます。

- `modeltaps.db`：SQLite データベース（`SQLITE_PATH`。既定では作業ディレクトリからの相対パス、すなわち `/data/modeltaps.db`）。ユーザーパスワードのハッシュ、ユーザートークン、チャネルの API キーなどが含まれます。アプリケーションは `0644` の権限でこのファイルを作成するため、既定では同じホストの他のユーザーも読み取れます
- `config.yaml`：`user_token_secret`、`session_secret`、`sql_dsn` などを平文で保存します
- `.env`：平文の秘密鍵
- `logs/`：上記のログファイル

::: tip 画像アップロードはローカルディスクに保存されません
画像ストレージへのアップロード（`STORAGE_*`）はすべてリモートサービス（sm.ms / imgur / Alibaba Cloud OSS / S3 プロトコル）へ直接送信され、Modeltaps はローカルにアップロード用ディレクトリを**作成しません**。そのためアップロード内容に個別の権限設定は不要です。保護すべきは、これらの画像ストレージ認証情報を保存する `config.yaml` / `.env` です。詳細は [画像ストレージ設定](./storage.md) を参照してください。
:::

### Docker / Docker Compose でのデプロイ

イメージ内では固定の非 root ユーザー `modeltaps`（UID/GID はいずれも `10001`）で実行されます。ホスト側マウントディレクトリの所有者をこれに合わせる必要があり、合っていないとコンテナに書き込み権限がありません。

```bash
# 所有者をコンテナ内の modeltaps(10001) に合わせる
sudo chown -R 10001:10001 /data/modeltaps

# マウントのルートディレクトリとログディレクトリ：所有者のみ読み書き実行可
sudo chmod 700 /data/modeltaps
sudo chmod 700 /data/modeltaps/logs

# 機密ファイル：所有者のみ読み書き可（ファイルが存在しない項目はスキップして構いません）
sudo chmod 600 /data/modeltaps/.env \
               /data/modeltaps/config.yaml \
               /data/modeltaps/modeltaps.db \
               /data/modeltaps/logs/modeltaps.log
```

ディレクトリを `700` にすると、ホスト上の一般的な運用アカウントはこれらのファイルを閲覧するのに `sudo` が必要になります。これが意図した動作です。

### ベアメタル（手動）デプロイ

root で直接実行しないでください。ログインシェルを持たない専用のシステムユーザーを作成し、インストールディレクトリをそのユーザーに割り当てることを推奨します。

```bash
# 専用のシステムユーザーを作成
sudo useradd --system --home-dir /opt/modeltaps --shell /usr/sbin/nologin modeltaps

# 所有者を専用ユーザーにし、ディレクトリは所有者のみ入れるようにする
sudo chown -R modeltaps:modeltaps /opt/modeltaps
sudo chmod 750 /opt/modeltaps
sudo chmod 700 /opt/modeltaps/logs

# 機密ファイルは所有者のみ読み書き可
sudo chmod 600 /opt/modeltaps/config.yaml \
               /opt/modeltaps/modeltaps.db \
               /opt/modeltaps/logs/modeltaps.log
```

このユーザーで起動します（`--log-dir` で権限を強化済みのディレクトリを明示的に指定し、プログラムが緩い umask で新規作成しないようにします）。

```bash
sudo -u modeltaps /opt/modeltaps/modeltaps --port 3000 --log-dir /opt/modeltaps/logs
```

::: tip 先にディレクトリを作成してから起動する
上記のコマンドで `logs` ディレクトリを先に作成し `700` に設定しておけば、プログラムが「`0777` で自動作成」する経路を通ることはありません。
:::

### 記録済みの初期パスワードを削除する

root のパスワードを変更した後も、初期パスワードはログ内に平文で残っているため、併せて削除する必要があります。

```bash
# 1. ログに該当行が存在するか確認する
sudo grep -l "initial root password" /data/modeltaps/logs/*.log

# 2. 該当行を含むログファイルを削除する（ローテーションで生成された履歴ファイルを含む）
sudo rm -f /data/modeltaps/logs/modeltaps.log /data/modeltaps/logs/modeltaps-*.log
```

コンテナの標準出力は Docker 自身のログファイルに別途保存されるため、上記のファイルを `rm` しても消えません。確認と削除の方法は次のとおりです。

```bash
# 確認
docker logs modeltaps 2>&1 | grep "initial root password"
# 削除：コンテナを再作成する（データはマウントされたボリュームにあるため失われません）
docker rm -f modeltaps && docker run -d ...   # 元の起動コマンドで再作成します
```

::: tip より確実な方法：初回起動前に ROOT_PASSWORD を設定する
**初回起動前**に `.env` で `ROOT_PASSWORD`（8〜64 文字。長さが要件を満たさない場合はプログラムが起動に失敗します）を設定すれば、プログラムはランダムパスワードを生成しません。ログには `password is set via ROOT_PASSWORD env` のみが出力され、パスワード自体は含まれません。[環境変数](./env.md#環境変数の説明) の `ROOT_PASSWORD` の項目を参照してください。
:::

## 管理者の緊急ログイン経路

アカウント体系を外部の**ID プロバイダー**に切り替えると、一般ユーザーは ID プロバイダー経由でしかログインできません。ID プロバイダーが利用できなくなったとき（鍵のローテーション、ドメイン変更、サービス終了、設定ミス）に誰も管理画面へ入れなくなることを防ぐため、Modeltaps は root アカウント向けに、ID プロバイダーに依存しないログイン経路を 1 本だけ残しています。

- **緊急入口**：外部 ID プロバイダーモードでは `/login/admin` に管理者用のログインフォーム（パスワードまたはパスキー）が表示され、通過できるのは root アカウントだけです。それ以外のアカウントが同じフォームから送信した場合はすべて拒否されます。この入口はパスワードログインとまったく同じ検証（アカウントロック、失敗回数のカウント、人間確認）を通るため、セキュリティレベルは下がりません。旧アドレス `/login?local=1` はここへ恒久リダイレクトされます。
- **無効にできます**：管理画面「システム設定 → ログイン方式 → 管理者の緊急ログイン」（`AdminLoginEnabled`、既定は有効）でこの入口を閉じられます。閉じると `/login/admin` と root の本サイトのパスワード・パスキーも使えなくなり、ID プロバイダーだけが唯一の経路になるため、プロバイダー側に災害対策があることを確認してから無効にしてください。
- **切り替えの前提**：外部 ID プロバイダーへ切り替える**前に**、root に強力なパスワード（16 文字以上、パスワードマネージャーで保管）を設定し、「設定 → ログインとセキュリティ → ログイン方法 → パスキー」でパスキーを 1 つ以上登録してください。ID プロバイダーに依存しない 2 本目の経路になります。
- **いつでもローテーション可能**：外部モードでも root は「設定 → ログインとセキュリティ → 管理者の緊急ログイン」でこのパスワードを変更し、パスキーを追加・削除できます。他のアカウントはこの状態では本サイトのパスワードを設定・変更できません。
- **`ROOT_PASSWORD` は初期値にすぎません**：この環境変数はデータベースの初回作成時（ユーザーがまだ存在しないとき）にのみ有効です。その後に変更・削除しても既存の root パスワードには影響しないため、緊急手段としては使えません。[環境変数](./env.md#環境変数の説明) の `ROOT_PASSWORD` の項目を参照してください。

## マルチサーバーでのデプロイ

### 事前準備

1. すべてのサーバーに必要なコンポーネントがインストールされていることを確認します。

- Docker、または手動デプロイに必要なコンポーネント
- Redis（キャッシュを利用する場合）
- MySQL クライアント（リモートの MySQL を使用する場合）

2. ネットワーク設定：

- すべてのサーバーがメインのデータベースにアクセスできることを確認する
- Redis を使用する場合は、Redis サーバーにアクセスできることを確認する
- サーバー間のファイアウォール設定を確認する

1. すべてのサーバーで `SESSION_SECRET` に同じ値を設定します。
2. `SQL_DSN` の設定が必須です。SQLite ではなく MySQL を使用し、すべてのサーバーが同一のデータベースに接続します。
3. すべてのスレーブサーバーで `NODE_TYPE` を `slave` に設定する必要があります。未設定の場合はマスターサーバーとして扱われます。
4. `SYNC_FREQUENCY` を設定すると、サーバーは定期的にデータベースから設定を同期します。リモートデータベースを使用する場合は、マスター・スレーブを問わずこの項目の設定と Redis の有効化を推奨します。
5. スレーブサーバーでは任意で `FRONTEND_BASE_URL` を設定し、ページリクエストをマスターサーバーへリダイレクトできます。
6. スレーブサーバーには**それぞれ**個別に Redis を導入し、`REDIS_CONN_STRING` を設定してください。これによりキャッシュが失効していない間はデータベースへのアクセスがゼロになり、レイテンシを削減できます。
7. マスターサーバーのデータベースアクセスのレイテンシも高い場合は、同様に Redis を有効化し、`SYNC_FREQUENCY` を設定して定期的にデータベースから設定を同期してください。
